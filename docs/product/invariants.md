# Invariants

Cross-cutting decisions captured once, referenced everywhere by ID. A rule belongs here iff all three: **cross-cutting** (bears on ≥2 places) · **load-bearing** (violating it breaks something real) · **stable** enough to name. Sources: `docs/design.md` §01–§06 and §23 Resolutions.

Operations: add = next number in category, never reuse · update = append dated note and amend every referencing spec · retire = mark DEPRECATED, never delete.

| INV-AUTH-1 | Two credentials only: a human session token (full control) and a per-project runtime token limited to five capabilities — fetch pipeline · claim lease · heartbeat · append spans · poll own-run status (the read that makes aborts land at the next tool call). The gap is enforced at the API, never in the UI. *(2026-08-12: added own-run status poll as the fifth capability; without it the §06 abort semantics were unimplementable.)* | Everything a machine may do must be a subset of what a human may do (design §04). | 2026-08-08 |
| INV-AUTH-2 | A runtime-token call to any privileged endpoint is refused loudly and written to the audit log — never silently dropped. | Silent rejection hides probing and misconfiguration (design §04). | 2026-08-08 |
| INV-AUTH-3 | Imported library items are untrusted until a human marks them reviewed; untrusted items never materialize, and compile is hard-blocked while any referenced item is untrusted. | Imports are the supply chain; compile is the approval point (design §04). | 2026-08-08 |
| INV-AUTH-4 | Runtime tokens reach runtimes two ways only: injected as an environment variable at supervisor spawn (headless), or stored in machine-local config by `surge auth` (interactive). A token never appears in a bound repo, a compiled file, or a backup. | `surge.yaml` is "never secrets"; the credential path must be as closed as the write path (design §23-Eleven). | 2026-08-12 |
| INV-AUTH-5 | Auth is never implied by reachability: first launch, restore, and rotation-to-zero mint the human session token only via a one-time claim URL printed to the terminal. | INV-DATA-3 | A published pipeline *version* is immutable; a pipeline advances only by publishing vN+1 from the builder. | INV-DATA-8 | All state lives in one embedded store (SQLite, ADR-2) inside the Surge process. | INV-ID-1 | Every materialization is identified by a content hash, and every run records the materialization hash it executed under. Stale materialization → dispatch refused. | A run must always trace back to the exact graph that produced it (design §03, §06). | 2026-08-08 |
| INV-ID-2 | The pipeline content hash covers semantic content only. **Node:** `id`, `human_gate`, and the semantic projection of `config` — pinned library references (name + version), `output_path`, hook `event`/`matcher`/`scope`, stage `command`, agent `fanout`, block `members`/`exposed_params`. **Edge:** `id`, endpoints, `trigger`, `gate_required`. Nodes and edges are sorted by id before hashing, so declaration order never matters. Everything else is presentation and never enters the hash: positions, `label`, collapse state, frames, stickies, annotations, and the observability fields `emits_span`, `metric_binding`, `metric_note`. **No client may reshape a hashed field** — normalizing, trimming, defaulting or re-sorting one silently changes a pipeline's identity, so any such normalization belongs server-side, before the hash, where every client sees it. | Canvas↔code hash fidelity (phase-1.1's headline test — it is that epic's whole thesis) is only satisfiable if presentation is excluded by rule, not by accident; two graphs that execute identically **and name the same nodes** must hash identically (design §23-Eight). | 2026-08-12 |

| INV-ID-3 | Each completed semantic project-canvas mutation atomically creates a durable project-local revision/hash, stales materialization and writes audit. The acknowledged revision is displayed beside the pinned assignment. Presentation-only edits persist without rehashing/staling. Pending/failed mutation is explicitly unsaved and prevents compile/dispatch; no optimistic graph is described as running. Undo/redo persists another mutation. Runs retain their immutable dispatched revision/materialization; promote-to-fork records provenance. *(2026-10-12: clarifies completed gesture vs pointer preview and failure acknowledgement; source versions remain immutable.)* | Saved authoring state and run identity must never pass through an unnamed graph. | 2026-08-12 |
| INV-ERR-1 | Every refusal (stale dispatch, token rejection, compile block, replay-on-compacted) produces a visible record — a run/span or audit entry carrying the reason string. Refuse loudly; never degrade silently. | Refusals are data; invisible refusals are bugs users can't report (design §06, §20). | 2026-08-08 |
| INV-OBS-1 | Every privileged act (approve, gate unlock/relock, review, assignment, compile, abort, rotation, credential/egress edit, revision, replay, ratchet) writes an audit entry: action, subject, actor, when. | The audit trail is the product's memory of human intent (design §03). | 2026-08-08 |
| INV-OBS-2 | Retention compaction may drop span bodies, never span structure — role, timings, status, cost and policy strings are kept forever; surfaces needing bodies show an explicit compacted placeholder, and replay is refused. | Metrics and traces must not decay into lies (§23-Five). | 2026-08-08 |
| INV-NAME-1 | UI vocabulary from design §01 is binding across code, docs and copy: pipeline, library, materialization, work order, Board·Plan, Board·Ops, observatory. No synonyms. | Shared nouns are what keep four views of one object one object. | 2026-08-08 |
| INV-DEPLOY-1 | Surge is one local single-user service, bound to loopback, with one distributable Rust binary containing UI/plugin assets; worker/runtime subprocesses are explicit dependencies. Hook/tool declarations alone are not sandbox enforcement. *(2026-10-12: replaces the false closed-network default with actual current posture. | INV-EXEC-1 | Headless workers are spawned only by Surge's runtime supervisor, and only for a dispatched issue holding a lease; every spawn records run id, materialization hash and work-order hash. Interactive sessions are human-launched and claim leases; Surge never drives an interactive session. | Dispatch semantics (queue policy, max-parallel, retry, budgets) are only real if Surge owns the actuator (design §23-Six). | 2026-08-12 |
| INV-EXEC-2 | One worktree per lease: claiming a lease creates a git worktree on the issue's task branch; the worker runs inside it, the materialization is compiled into it, and the worktree is reaped when the lease ends. Parallel workers never share a working directory. | "Max 3 parallel" is only safe with isolation, and wave integration needs a defined place to rebase from (design §23-Ten). | 2026-08-12 |
| INV-EXEC-3 | Orchestration state transitions (verified, failed, retry, budget breach) derive only from Surge-observed facts — process exit codes, deterministic stage results, supervisor-side metering. Span content is observability, never control flow. A run whose cost cannot be metered is treated as over-cap and paused behind the budget-breach gate. *(2026-10-12: 1.2 proves per-run metering/gating before graph automation; 2.2 extends it to role/wave budgets. ## Amendments

### INV-ID-2 — dated amendments

**2026-08-29 (ESC-4).** The executable form **moved crates**: `pipeline_content_hash` and its `Semantic*` projection now live at `crates/domain/src/hash.rs`, exported as `surge_domain::pipeline_content_hash`. **The rule is unchanged and the output is unchanged** — the fixture pipeline hashed to `sha256:796565e8138a76f516d5a4fc71440b2526a7cf11bd301a4fff965d4e6de8a29d` before the move and after it, and `crates/domain/tests/hash.rs` now pins that literal so a future edit to the projection cannot land quietly. The move exists so that identity can be derived where the graph is: `surge_store::pipelines::insert_graph` computes the hash of the graph it inserts instead of storing the one it is handed, and `surge_domain::fixtures::two_node_pipeline()` states its own. `materialization_hash` (INV-ID-1) stayed in `surge-compiler` — it hashes emitted `CompiledFile` bytes, which the object model has no type for. Line anchors in the 2026-08-28 entry below still read `hash.rs:NN`; they refer to the pre-move file and are kept verbatim as the dated record.

**2026-08-28 (phase-1.1 spec sprint, canvas-editor review).** The rule was restated to match `crates/compiler/src/hash.rs`, which is the executable form of this invariant. Four corrections, each verified against the code rather than against a spec:

1. **"prompt bodies" removed from the covered list — it was never true of this hash.** `SemanticConfig` embeds `LibraryRef { name, version }` only (`hash.rs:28-39`); an item's `body` (`crates/domain/src/library.rs:16`) never reaches `pipeline_content_hash`. Bodies enter identity **transitively and one level down**: INV-DATA-2 makes an item immutable per version, so `(name, version)` is a stable handle on a body, and `materialization_hash` covers the emitted bytes directly (`hash.rs:100-116`, `h.update(f.contents)`). The guarantee is real; the old wording located it in the wrong hash. Anyone reading "the pipeline hash covers prompt bodies" would have concluded that editing a subagent body re-hashes every pipeline pinning it. It does not — that is what the upgrade review exists for.

2. **Node and edge `id` are hash inputs, and the rationale is narrowed to say so.** `SemanticNode.id` and `SemanticEdge.id` are both hashed (`hash.rs:61-74`). The old rationale — "two graphs that execute identically must hash identically" — was therefore false as written: consistently renaming every node produces an identically-executing graph with a different hash. Ids are not decoration; edges and `Block.members` reference them, so they carry structure. The rationale now reads "**and name the same nodes**". The consequence is load-bearing for phase-1.1: a graph *independently redrawn* from scratch does **not** hash the same as its pasted text unless the ids are carried across. Canonicalizing ids away would be `role:critical` and was not done.

3. **The three observability fields are named explicitly.** `emits_span`, `metric_binding` and `metric_note` sit on `Node` outside `config` (`crates/domain/src/pipeline.rs:36-40`), are excluded from the hash (`hash.rs:61-65`), and that exclusion is locked in by test (`crates/compiler/tests/compile.rs:57`). The old presentation list named none of them, so their status rested on a reader inferring it. **Standing condition:** nothing in `crates/compiler` reads `emits_span` today — it is persisted and reloaded and otherwise inert (verified by grep, 2026-08-28). The moment it actually drives span emission it becomes semantic, and leaving it out of the hash would break this invariant's own rationale. Whoever wires it up must move it into `SemanticNode` in the same change.

4. **"No client may reshape a hashed field" is promoted into the rule.** It arose as a canvas-editor constraint but binds every surface that mutates a graph from the generated types — `code-roundtrip`, `blocks-and-groups`, `upgrade-review`. It is cross-cutting, load-bearing and stable, so it belongs here rather than being restated per spec. It has teeth: it forbids client-side trimming of `Stage.command` and coercing an empty `fanout` to `0`, both of which are genuine ergonomic losses, and both of which would change identity invisibly.


### Execution and Block clarification — 2026-10-12

INV-ID-2 is unchanged: block membership/exposed parameters are semantic; visual grouping and collapse/layout are presentation. Creating or changing a Block may change identity; an unchanged round-trip must preserve it. The executable hash is not changed by this replan.

Hash fidelity alone does not establish scheduling semantics. The executor must validate its supported graph, freeze revision/materialization at dispatch, attribute node attempts, and choose transitions from observed outcomes under INV-EXEC-3. Unsupported executable kinds refuse visibly. See [roadmap](../phases/README.md) and design §23-Twenty-Four onward.
