# Invariants

Cross-cutting decisions captured once, referenced everywhere by ID. A rule belongs here iff all three: **cross-cutting** (bears on ≥2 places) · **load-bearing** (violating it breaks something real) · **stable** enough to name. Sources: `docs/design.md` §01–§06 and §23 Resolutions.

Operations: add = next number in category, never reuse · update = append dated note and amend every referencing spec · retire = mark DEPRECATED, never delete.

| ID | Rule | Rationale | Since |
|---|---|---|---|
| INV-AUTH-1 | Two credentials only: a human session token (full control) and a per-project runtime token limited to five capabilities — fetch pipeline · claim lease · heartbeat · append spans · poll own-run status (the read that makes aborts land at the next tool call). The gap is enforced at the API, never in the UI. *(2026-08-12: added own-run status poll as the fifth capability; without it the §06 abort semantics were unimplementable.)* | Everything a machine may do must be a subset of what a human may do (design §04). | 2026-08-08 |
| INV-AUTH-2 | A runtime-token call to any privileged endpoint is refused loudly and written to the audit log — never silently dropped. | Silent rejection hides probing and misconfiguration (design §04). | 2026-08-08 |
| INV-AUTH-3 | Imported library items are untrusted until a human marks them reviewed; untrusted items never materialize, and compile is hard-blocked while any referenced item is untrusted. | Imports are the supply chain; compile is the approval point (design §04). | 2026-08-08 |
| INV-AUTH-4 | Runtime tokens reach runtimes two ways only: injected as an environment variable at supervisor spawn (headless), or stored in machine-local config by `surge auth` (interactive). A token never appears in a bound repo, a compiled file, or a backup. | `surge.yaml` is "never secrets"; the credential path must be as closed as the write path (design §23-Eleven). | 2026-08-12 |
| INV-AUTH-5 | Auth is never implied by reachability: first launch, restore, and rotation-to-zero mint the human session token only via a one-time claim URL printed to the terminal. Any loopback process can reach the port; none is trusted for it. | Spawned workers share the loopback; "whoever curls first" must not win the instance (design §23-Sixteen). | 2026-08-12 |
| INV-AUTH-6 | Model-provider API keys are Surge-side credentials: stored in the instance registry, injected into workers as env vars at spawn, never written to a bound repo, a compiled file, or a backup. Provider hosts are auto-appended to the worker sandbox allowlist and shown on the capability report's egress line. *(2026-08-26 smoke walk 5, invariant audit: the allowlist clause is a decision, not a shipped behaviour — it depends on the INV-DEPLOY-1 sandbox and the project egress allowlist, neither of which exists; `crates/compiler/src/capability.rs` emits one hardcoded egress line today. Provider-key storage and injection are likewise Phase 3 settings work. Read this row as binding on the design, not as a description of the binary.)* | A model provider is both a credential and an egress path; hiding either breaks the §04 trust story (design §23-Twenty-One). | 2026-08-23 |
| INV-DATA-1 | Exactly five things may be written into a bound workplace repo: `surge.yaml`, compiled `.claude/` runtime files, docs at paths the pipeline's doc nodes declare, rendered work-order files under `work_orders/`, and the surge-managed block inside the repo-root `.gitignore` — that block only, delimited by its markers, with every surrounding line preserved byte-for-byte. Closed list — extending it is a spec change. *(2026-08-12: added `work_orders/` as the fourth item; design §01/§03 already required the file, the list had simply never been amended.)* *(2026-08-26 smoke walk 5, invariant audit: added `.gitignore` as the fifth item. INV-DATA-7 has required the compiler to maintain that block since 2026-08-12 and `crates/compiler/src/write.rs::upsert_gitignore_block` has always created or rewritten the file, so the two invariants contradicted each other and the shipped code violated the closed list on every compile. Enumerating the write is the honest fix: the alternative — softening the list to "four kinds plus whatever INV-DATA-7 needs" — would stop it being closed, which is the whole point of the rule. The narrow scope is load-bearing: outside the markers the compiler may not touch a byte, so a hand-written `.gitignore` survives every compile.)* | The repo is the runtime's filesystem, not Surge's database (design §01). | 2026-08-08 |
| INV-DATA-2 | Library items are immutable per version; pipelines pin a version and never move until explicitly bumped via the upgrade review. | Pinning is what makes a materialization hash meaningful (design §05, §23-Two). | 2026-08-08 |
| INV-DATA-3 | A published pipeline *version* is immutable; a pipeline advances only by publishing vN+1 from the builder. Forking is divergence without advancing the original: blessed templates are untouched by forks, and project-canvas edits promote to a fork rather than pushing back. *(2026-08-12: restated — "fork, never edit in place" contradicted templates carrying version history; the immutable unit is the published version, not the pipeline name. Design §23-Seventeen.)* | Provenance and blast-radius control (design §05, §23-One). | 2026-08-08 |
| INV-DATA-4 | An approved taskgraph is amended by diff, never re-expanded; done and in-flight work is never touched by an amendment. | Regeneration would orphan live work (design §05). | 2026-08-08 |
| INV-DATA-5 | The Plan board is a read-only mirror; Plan and Ops never write each other's status. Contradictions are surfaced as a diverged badge and a "Needs you" item, never auto-reconciled. *(2026-08-23: when the tracker is built-in, Plan is that tracker's authoring surface — creates/edits write tracker records, never orchestration status; design §23-Twenty.)* | Two writers to one status field is how boards lie (design §03, §23-Four). | 2026-08-08 |
| INV-DATA-6 | Surge reads from a bound repo exactly three things: files at declared doc-node paths (ingested and hashed after a doc node's run completes — the repo file is canonical, Surge's copy is a projection), `work_orders/` files (for hash-mismatch checks), and git state (branches, commits, PR metadata) for wave integration. Closed list, mirroring INV-DATA-1's write list (three reads against five writes — the lists mirror in discipline, not in length). | Docs surfaces, work-order refusals and wave assembly all require reads the architecture must own explicitly, with the same discipline as writes (design §23-Seven). | 2026-08-12 |
| INV-DATA-7 | Git policy per write kind: `surge.yaml` and pipeline-declared docs are committed; compiled `.claude/` files and `work_orders/` are gitignored — reproducible from the materialization hash, compiled into each worktree, never merge material. The compiler maintains the ignore entries inside a marked surge-managed block — enumerated as INV-DATA-1's fifth write kind since 2026-08-26. | A uniform answer breaks either wave rebase (generated churn) or fresh worktrees (no materialization); the deliverables must be committed, the reproducible must not be (design §23-Twelve). | 2026-08-12 |
| INV-DATA-8 | All state lives in one embedded store (SQLite, ADR-2) inside the Surge process. A change spanning entities — approving a taskgraph, compiling, unlocking a gate — commits as one transaction together with its audit entry. No second datastore, no derived cache permitted to disagree with it. *(2026-08-25: store re-decided as SQLite; the invariant was and is store-agnostic — one embedded store, one transaction boundary.)* | A half-landed privileged act would break INV-OBS-1's audit guarantee and INV-ID-1's run→graph traceability (ADR-2). | 2026-08-18 |
| INV-ID-1 | Every materialization is identified by a content hash, and every run records the materialization hash it executed under. Stale materialization → dispatch refused. | A run must always trace back to the exact graph that produced it (design §03, §06). | 2026-08-08 |
| INV-ID-2 | The pipeline content hash covers semantic content only: nodes (kind, config, prompt bodies, gates, fanout), edges (endpoints, triggers, gate flags), and pinned library references (name + version). Presentation state — positions, frames, stickies, annotations, collapse state — never enters the hash. | Canvas↔code hash fidelity (Phase 1's headline test) is only satisfiable if annotations are excluded by rule, not by accident; two graphs that execute identically must hash identically (design §23-Eight). | 2026-08-12 |
| INV-ID-3 | A project-canvas edit immediately creates a project-local revision with its own content hash, recorded beside the pinned assignment (`v14 + local rev 9c4e…`). Runs record the local revision hash; promote-to-fork names it. A project is never described as running plain `vN` while local edits exist. | INV-ID-1's run→graph traceability must not pass through an unnamed graph (design §23-Nine). | 2026-08-12 |
| INV-ERR-1 | Every refusal (stale dispatch, token rejection, compile block, replay-on-compacted) produces a visible record — a run/span or audit entry carrying the reason string. Refuse loudly; never degrade silently. | Refusals are data; invisible refusals are bugs users can't report (design §06, §20). | 2026-08-08 |
| INV-OBS-1 | Every privileged act (approve, gate unlock/relock, review, compile, abort, rotation, credential/egress edit, revision, replay, ratchet) writes an audit entry: action, subject, actor, when. | The audit trail is the product's memory of human intent (design §03). | 2026-08-08 |
| INV-OBS-2 | Retention compaction may drop span bodies, never span structure — role, timings, status, cost and policy strings are kept forever; surfaces needing bodies show an explicit compacted placeholder, and replay is refused. | Metrics and traces must not decay into lies (§23-Five). | 2026-08-08 |
| INV-NAME-1 | UI vocabulary from design §01 is binding across code, docs and copy: pipeline, library, materialization, work order, Board·Plan, Board·Ops, observatory. No synonyms. | Shared nouns are what keep four views of one object one object. | 2026-08-08 |
| INV-DEPLOY-1 | Surge is one process, one static binary, bound to loopback (`127.0.0.1:7420`) only; hooks and stages get no network unless the host is on the project egress allowlist, checked at dispatch. `127.0.0.1:7420` itself is implicitly exempt from the allowlist — the runtime's own hooks (span emission, guards, status polls) must always reach Surge, and the exemption is stated in the capability report rather than hidden. *(2026-08-12: loopback exemption made explicit; without it the shipped `emit-span` hook was unusable under the "empty — all egress refused" default.)* *(2026-08-23: enforcement **decided** as two-tier per design §23-Nineteen — processes Surge spawns are to run inside an OS-level network sandbox; runtime-side hook scripts are to be declared + audited, with the capability report labelling each line `enforced` or `declared`.)* *(2026-08-26 smoke walk 5, invariant audit: read the 2026-08-23 note as a resolution, not a guarantee — none of it is implemented. There is no Seatbelt profile, no `sandbox-exec` invocation and no network namespace anywhere in `crates/`; `crates/compiler/src/capability.rs` emits one hardcoded egress line — "empty — all egress refused (loopback to Surge always allowed)" — for every project, with no per-line tier label and no allowlist to check at dispatch. What phase 0 actually ships is the closed **default** and the stated loopback exemption. The sandbox, the project egress allowlist and the `enforced`/`declared` labels land with Phase 2; until the label exists, the "degrades visibly to declared" fallback cannot be visible.)* | Local-only single-operator is the security model (design §01, §04). | 2026-08-08 |
| INV-EXEC-1 | Headless workers are spawned only by Surge's runtime supervisor, and only for a dispatched issue holding a lease; every spawn records run id, materialization hash and work-order hash. Interactive sessions are human-launched and claim leases; Surge never drives an interactive session. | Dispatch semantics (queue policy, max-parallel, retry, budgets) are only real if Surge owns the actuator (design §23-Six). | 2026-08-12 |
| INV-EXEC-2 | One worktree per lease: claiming a lease creates a git worktree on the issue's task branch; the worker runs inside it, the materialization is compiled into it, and the worktree is reaped when the lease ends. Parallel workers never share a working directory. | "Max 3 parallel" is only safe with isolation, and wave integration needs a defined place to rebase from (design §23-Ten). | 2026-08-12 |
| INV-EXEC-3 | Orchestration state transitions (verified, failed, retry, budget breach) derive only from Surge-observed facts — process exit codes, deterministic stage results, supervisor-side metering. Span content is observability, never control flow. A run whose cost cannot be metered is treated as over-cap and paused behind the budget-breach gate. | The machinery must not branch on data the supervised side wrote; self-reported passes and costs are how orchestrators get lied to (design §23-Thirteen). | 2026-08-12 |
