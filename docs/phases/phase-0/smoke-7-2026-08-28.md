| W1 | P3 | **Surge now fails a run for not committing, but nothing on the worker's critical path tells it to commit.** The full instruction a worker receives is "Complete the task described by this issue on its task branch. Filed because the enforcement is silent and the incentive unstated | one line in `crates/compiler/src/work_order.rs:10-11` or the prompt suffix at `supervisor.rs:397-402`; the work-order hash is content-derived, so pinned `work_order_hash` fixtures move with it |

**W1 is not the known limitation.** The documented carve-out at `supervisor.rs:719-733` covers legitimately commit-free work-order *kinds*. W1 is the opposite: a commit-expected work order whose requirement never reaches the worker.

## Workaround language the walker caught itself writing

Surfaced rather than buried, per the report format. While constructing four issues the walker wrote instructions the shipped system does not supply — *"Committing is required: the work is not done until it is committed"* and *"call `surge_heartbeat` at least three times over the run"*. Both are "say X or you won't get Y" standing in for missing product behaviour.

Neither was graded P0, on evidence rather than judgement: the commit one is downgraded to W1/P3 because uncoached controls committed anyway; the heartbeat one is downgraded to **nothing**, because the same uncoached controls called `surge_fetch_work_order` and `surge_poll_run` unprompted and a real lease was extended four times. The tooling is discoverable without coaching. Recorded so the next walker can check whether that still holds.
